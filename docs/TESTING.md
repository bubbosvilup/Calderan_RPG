**Authoritative runs (Repository Cleanup A).** `npm test`, `npm run benchmark:modern` and every `npm run <tool>` that runs compiled code go through `npm run build`, which deletes `.build/` first, exactly once (there are no npm lifecycle hooks). `.build/` is disposable compiled output only, never evidence: a compiled test whose source was deleted is gone before `node --test` discovers tests (`tests/tooling/build-discipline.test.ts`). Never run two builds or test runs at the same time in one checkout. **Where files belong (Repository Cleanup B2).** Executable test fixtures live under `tests/fixtures/` (the ones copied from historical evidence are listed with their source and sha256 in `tests/fixtures/provenance.json`). Local output, private and public, goes to the gitignored `artifacts/local/`; tools write new evaluation runs to `artifacts/local/evaluations/`. Committed evidence lives under `docs/evaluations/` and enters it only by a deliberate copy; nothing executable reads it. `tests/architecture/evaluation-history-isolation.architecture.test.ts` fails if a test, production module or tool uses `docs/evaluations/` as a path, except four historical reproduction tools it allowlists (`src/dev/historical/eval-evidence.ts`, `src/dev/historical/shadow-evidence.ts`, `scripts/historical/d09-*.mjs`, `scripts/historical/minor-debt-controller-audit.mjs`; the D09 reflection evidence they use is in `docs/evaluations/d09-reflection/evidence/`).

**Browser checks.** `scripts/browser/*-browser-check.mjs` are offline real-browser checks (all drive the React UI: `react-play`, `react-ui2`, `react-ui3`, `react-people`, `react-background`, `react-reliability`). Run `npm run build` (and `npm run ui:build` for the React ones) first, then `node scripts/browser/<name>-browser-check.mjs`, or run all six, one at a time, with `npm run check:browser` (`npm run check:browser -- react-ui2 react-people` selects by file prefix). Paths come from `scripts/lib/browser-env.mjs` (repository-relative). Playwright is the pinned devDependency `playwright@1.56.1` (`PLAYWRIGHT_MODULE` or `NODE_PATH` still override it); `npm install` never downloads a browser, so run `npx playwright install chromium` once (Linux: add `--with-deps`) or set `CHROMIUM_PATH`. CI never uses `CHROMIUM_PATH`: the job installs Playwright's own Chromium, so the browser is the one the pinned Playwright version expects. Every check asserts its outcome and exits non-zero on a wrong result (B2 made the last two report-only checks, confirmation and turn reliability, assert). Screenshots go to `artifacts/local/browser/<check>/`.

**Fast gate and CI.** `.github/workflows/fast.yml` (GitHub Actions; Linux and Windows; Node 22) runs on every pull request and every push to main, on Linux and Windows, in this order: `npm ci`, `npm run typecheck`, `npm run check:architecture`, `npm run check:docs`, `npm run check:scripts` (`node --check` over every script under `scripts/`), `npm run ui:typecheck`, `npm run ui:test`, `npm test` (the only run of the heavy suite; it builds `.build`), `node .build/tests/benchmark/run.js` (the modern benchmark on that same build; locally `npm run benchmark:modern`, which rebuilds first), `npm run ui:build`, the Chromium install (`npx playwright install --with-deps chromium` on Linux, `npx playwright install chromium` on Windows) and `npm run check:browser`. It is offline: no secrets, no provider call, no image call (the portrait pipeline runs against a scripted fake generator). Screenshots upload only when a job fails. The Windows leg is written to the same commands but was not exercised from the Linux development sandbox; the first Actions run is its proof. Local equivalent of the whole job: the same commands in the same order, with `npm run check:browser` last.

### Timing budgets (frontend)

The first render of every Vitest file and the first page load of every browser check are cold, and a loaded Windows runner is several times slower than Linux (on CI the first test of three files took just over Testing Library's default 1 s). So `src/ui-client/test/setup.ts` gives asynchronous queries (`findBy*`, `waitFor`) 5 s and `vite.config.ts` gives a test 20 s, and the first navigation of a browser check waits up to 30 s. These are time budgets only: assertions are unchanged, and a test that needs to wait for a state waits for that state, never for a fixed sleep. Do not lower them to make a run faster; fix a slow test at its cause.

## Test taxonomy

Repository Cleanup F (2026-10-13) organized the executable tests by the behavior or contract they protect, not by the milestone that introduced them. The move map, per-file discovery proof and the reasons are in [`REPOSITORY_CLEANUP_F_TEST_TAXONOMY.md`](evaluations/REPOSITORY_CLEANUP_F_TEST_TAXONOMY.md).

- **Where tests live.** Every executable test is `tests/<domain>/<behavior>.test.ts`, one level deep: `architecture`, `authority` (Controller authorization, evidence, audit, confirmations, knowledge permission), `canon` (authored world content), `commerce`, `context` (Narrator context, scene projection, compaction, grounding), `identity`, `images`, `items`, `language` (shared text primitives and gates), `movement`, `npc-plus`, `optional` (optional services, side stores, mannerisms), `persistence`, `providers`, `reflection`, `retrieval`, `session`, `tooling` (dev, benchmark and historical-replay tools), `turn` (the coordinator pipeline), `ui`, `world`. No test sits at the `tests/` root. A NarrationFacts suite lives with the domain whose facts it reads (`tests/movement/movement-narration-facts.test.ts`, `tests/commerce/commerce-narration-facts.test.ts`, `tests/identity/identity-narration-facts.test.ts`).
- **Names.** A file name says what it protects (`canonical-identity-gating`, `trade-offer-authorization`), never `block`, `pass`, `phase`, `pNN`, `consolidation`, `hotfix` or `wave`. Test titles carry the behavior too; requirement case labels (`A1`, `P12`, `I4`) and debt IDs (`AUTH-2`, `NARR-1`) are traceability labels and stay. A short provenance in parentheses (`(Phase 1M.1 replay regression)`) may name where a regression was first seen.
- **Suffixes.** `*.architecture.test.ts`: structural guards over source, imports or repository layout, and only those, all in `tests/architecture/`. `*.integration.test.ts`: a whole application path end to end (session host, HTTP, confirmation flow). `*.regression.test.ts`: a suite that pins specific recorded bugs (exact live drafts, replay findings). Everything else is plain `*.test.ts`; a file gets a suffix only when the suffix adds information.
- **Support code.** Shared test helpers and fixture builders are in `tests/support/` (`turn-fixtures.ts`, `world-fixtures.ts`, `turn-reliability-fixtures.ts`, `follow-household-harness.ts`, `import-graph.ts`, ...). Source-level audits list files with `sourceFiles()` and normalize any other path with `toPosixPath()` (`tests/support/source-paths.ts`) before matching, so their POSIX patterns hold on Windows (`\`) and Linux alike (`tests/tooling/source-paths.test.ts` pins both syntaxes). Runnable historical evaluation tools that used to sit beside the tests keep their historical names (reports cite them) in `tests/support/historical/`; run them with `npm run build` and `node .build/tests/support/historical/<name>.js`. Data fixtures stay in `tests/fixtures/` (B2 provenance), frozen oracles in `tests/frozen/`, golden files in `tests/golden/`, the curated playthrough in `tests/playthrough/`, the modern benchmark in `tests/benchmark/` and the retrieval evaluation in `tests/retrieval-eval/`. Fixtures and helpers shared with dev tools stay in `src/dev/support/`.
- **Historical identity.** Frozen oracle tests keep the oracle version in their name (`tests/reflection/reflection-v2-oracle.test.ts` .. `reflection-v23-oracle`), and historical-replay tests in `tests/tooling/` keep the replay labels their frozen artifacts carry (`D05`, `Phase 1M.1`).
- **Guard.** `tests/architecture/test-taxonomy.architecture.test.ts` fails when a test is added at the root or in an unknown folder, when a current test or support module is named for a milestone, when the `.architecture` suffix is used outside `tests/architecture/`, when a helper sits outside the support / fixture folders, or when `npm test` stops discovering folders recursively. A new domain folder is a deliberate change to its `DOMAINS` list and to this section.
- **Lifecycle words.** A test that checks PROVISIONAL → PERSISTENT says *materialize*; *promote* is only Campaign NPC → NPC+ (the Heartstone rite), plus the unrelated mannerism and narrator-focus senses. `tests/architecture/lifecycle-vocabulary.architecture.test.ts` (Repository Cleanup G) fails if the materialization primitive is named as a promotion again or writes NPC+ state.

- **Supported surface.** A tool is active only when an npm script exposes it, a current document tells you to run it, a current test imports it as support, an active tool imports it, or it belongs to a current certification. Everything else is in a `historical/` folder. Run a historical tool directly (`npm run build`, then `node .build/src/dev/historical/<name>.js` or `node scripts/historical/<name>.mjs`); some of them print usage text that still names their removed npm alias.
- **Live versus offline.** `npm test`, `npm run benchmark:modern` and the browser checks never call a provider. Live tools need `NODE_USE_ENV_PROXY=1` and a key (`OPENROUTER_API_KEY=placeholder` inside the sandbox, where the proxy injects auth).
- **Where output goes.** Every active tool writes under `artifacts/local/` (ignored by git) or the OS temp directory. The live certifications keep their scratch saves under `artifacts/local/evaluations/<harness>/`. The one listed exception is `extract:playthrough`, which regenerates `tests/playthrough/curated.json` on purpose. No active tool reads or writes `docs/evaluations/`. Only the four historical reproduction tools listed in `tests/architecture/evaluation-history-isolation.architecture.test.ts` may read or write there.
- **Archive policy.** `docs/evaluations/` is historical evidence. Nothing is deleted from it silently: reports are not rewritten, unique provider output, referenced screenshots and provenance manifests stay, and duplicates are removed only when nothing references them. The Cleanup E audit is in [`REPOSITORY_CLEANUP_E_DEV_TOOLING_ARCHIVE.md`](evaluations/REPOSITORY_CLEANUP_E_DEV_TOOLING_ARCHIVE.md).

## Player-authorized actions: how to test

- **Heartstone:** explicit-action tests (`tests/npc-plus/explicit-promotion.test.ts`) replaced the semantic oath-matcher tests; prose never promotes.
- **Actual Offer** (`tests/commerce/actual-offer.test.ts`, `src/ui-client/features/trade/*.test.tsx`): test separately offer interpretation (goods G, negotiation N, person P, negatives for auction/silver/questions/hypotheticals), UI presentation, identity masking (security regression), acceptance settlement and atomicity, idempotency, persistence (save/load) and browser behavior. Offline browser check: `node scripts/browser/react-play-browser-check.mjs` (scripted narrator/controller, zero live calls).
- **Identity:** `tests/identity/foreground-canonical-binding.test.ts`, `tests/commerce/person-offer-playthrough.regression.test.ts` (spoken price forms, stable subject, Slave NPC on Accept, rename). Live certification harnesses `src/dev/live/identity-live-cert.ts` and `src/dev/live/person-offer-live-cert.ts` spend credits and are never run by `npm test`.
- **Future certification policy.** A transcript-only replay cannot certify player-authorized actions (the frozen 421-turn oracle is historical and is not modified). A future ~100-turn benchmark should be designed against the current architecture with a scripted **action log**: per relevant turn the player input, Narrator response, Controller result, any explicit player action (`accept_trade_offer`, `completeHeartstoneRite`, save/load) and the expected authoritative delta, plus the expected final state.
