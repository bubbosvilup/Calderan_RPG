## 1. Summary

- The item domain has a solid **instance** foundation: engine-allocated stable IDs, one position per item, owner independent of carrier, derived inventory, seven transfer modes, atomic settlement that transfers the same item on a sale. What it lacks is everything about **amount and nesting**: no quantity, no stack, no kind key, no weight, no container, no sub-location. Property/containers sits exactly on that gap.
- Of the 15 rows reviewed, 12 are confirmed open as the register states, 1 is partial as the register states (TRD-7), 2 need the human decision the register names (ECO-1, TRD-11). One row is better than the register says: **ITM-6 is PARTIAL, not open**, because a typed `/equip` command exists (`src/turn/player-intent.ts:84-87`); it is just unusable in practice for engine-created items.
- Two register remedies need correcting. **ITM-2**: `empty_slots` is not purely derived; it also stores "known empty" slot knowledge (`src/campaign/projections.ts:40`, `src/campaign/characters.ts:87-94`), so "compute, do not persist" is only half right. **ECO-1 / D3**: the recommendation "schema 7" is stale; the in-memory snapshot is already schema 7 (`src/campaign/validation.ts:286`) and the save file is schema 8 (`src/persistence/save-format.ts:42`), so a currency change is the next schema bump, not schema 7.
- New small findings: the header comment of `src/campaign/trade.ts:15-16` still says goods SELL removes the item and "the buyer keeps nothing", which contradicts the code at `:188-205`; `ACTUAL_OFFER.md:71` says auction wording is rejected the same way on both paths, but the person path uses a stricter condition (`src/turn/commerce/person-offers.ts:53`); a third, separate auction regex lives in `src/economy/economy.ts:98`.
- Pruning `trade_offers` (TRD-12, not in scope but adjacent) is not independent of this work: accepted offers are the only goods money trail (TRD-11), and offer IDs are allocated as "highest existing plus one" (`src/campaign/trade.ts:145`), so pruning the newest closed offer could let an ID, and therefore its opaque UI ref (`src/app/trade-offer-view.ts:38`), be reused (inferred, not confirmed by execution).
- There are **no authored item templates** in `data/`: a type count over all YAML finds characters, locations, factions, concepts and world lore, and zero `type: item`. The authored world schema does support canonical items with `owner`, `location` or `container` (`src/world/validation.ts:212-214`, `:315-320`, `:333-336`), but nothing uses it and `register_item` would not carry the container into campaign state (`src/campaign/items.ts:53-67`).
- Property ownership today is prose plus a document item: Nicco "starts as lawful owner" (`docs/CURRENT_STATE.md:72`) and carries a `Deed of Ownership` item (`src/campaign/opening-state.ts:33-34`). No structured location or property ownership exists. Inferred, not confirmed by execution: the deed is an ordinary owned and carried document, so nothing in the SELL preconditions (`src/campaign/trade.ts:127-134`) stops it from being sold into external custody.

## 6. Recommended implementation order

This is a proposal for the user to approve or change. Nothing here is scheduled.

1. **Zero-risk alignment (documentation and comments only).** Fix DOC-12 in `ACTUAL_OFFER.md`, the stale `trade.ts` header, the "schema 7" wording in D3, and the ITM-2 and TRD-6 remedy texts in the register. This keeps the following steps from being planned on wrong statements. Optionally TRD-13 (delete the unused `"purchase"` kind, rename `ACCEPT`, add the import guard), which is small and isolated.
2. **Decide the localization model before writing code (needs user decisions, see section 8).** The container shape (`contained{item_id}` position variant, as `ITEM_DOMAIN.md:137` proposes, or a `container_id` field, as the register and roadmap say), whether a household or a property can own an item, and whether property ownership becomes a structured record instead of the deed item alone.
3. **Equipment slot domain: ITM-1 with ITM-2.** A canonical slot set and the `headwear`/`footwear` categories, validated in `place()`, rendered from `position.slot`; settle what `empty_slots` means at the same time, because the same function (`src/campaign/items.ts:13-28`) owns both. Route the SELL path's slot bookkeeping (`src/campaign/trade.ts:197-200`) through the same code.
4. **ITM-6: a usable equip and unequip action.** A UI-confirmed engine action keyed by the item, not by a one-word name. It depends on step 3 for a closed slot list.
5. **ITM-4 and the quantity half of ITM-5: kind key and quantity.** One schema change: a `quantity` on item instances with clear split and merge rules, and a kind key that replaces name-string identity in the create dedupe (`command-authorizer.ts:50`) and the settlement veto (`trade-authorization.ts:134`). This should come before containers, because moving part of a stack into or out of a container needs split semantics.
6. **ITM-3 minimum: possession invariant and owner kinds.** One effective-location resolver (with a containment walk once step 7 lands) used by `itemHolder`, inventory queries, authorization and offer invalidation, plus the owner-kind decision from step 2. Full loan and theft records can wait for stage 2.
7. **Property/containers (the product item).** The container position, storage at Heartstone rooms and furniture, and the Property UI, built on steps 3 to 6. If the snapshot schema is bumped for steps 3 to 7 together, that is also "the next schema bump" that decision D6 (NAME-1 / PER-6 rename) is waiting for; the two should be planned together.
8. **Stage 2, robust transfers.** Persisted custody reasons and loan records (rest of ITM-3), tighter goods-name and category matching (TRD-6), withdrawal tied to the offer's subject or price (TRD-8).
9. **Stage 3, economy and transaction history.** Decision D3 first, then in one schema bump: the currency unit (ECO-1), a generic ledger with goods rows (TRD-11), the funds ledger with causes (ECO-4), and safe pruning of closed offers (TRD-12) with a persisted offer sequence so IDs are never reused. Then the anchor sanity band (ECO-2), the auction venue flag and one auction rule (TRD-7), and world-time expiry once vendors exist (TRD-14). Merchant wallets and stock follow the roadmap's T-ECON order (`docs/MASTER_ROADMAP.md:68`).
10. **Stage 4, world event ledger.** Reuse the ledger entry shape from step 9 rather than designing a second one.

TRD-12 is a P2 persistence item (it drives PER-1). If the save size becomes a problem before stage 3, a safe interim exists: superseded, withdrawn and invalidated offers carry no settlement (`src/campaign/snapshot-validation.ts:159`) and could be pruned without losing the money trail, provided the offer ID allocator stops depending on the highest existing ID first (`src/campaign/trade.ts:145`). That is an inference from reading, not confirmed by execution.

## 7. Debt that must be solved before Property/containers

**Must be solved first (item debt):**

1. **ITM-5, container model decision.** Choose the containment shape and the effective-location rule before any storage code. Without it every helper that asks "who holds this" (`src/campaign/item-transfer.ts:5-7`, `src/campaign/inventory.ts:25-43`, `src/campaign/trade.ts:69`) gives the wrong answer for an item inside a carried bag. The implementation of containers itself is the Property work.
2. **ITM-4 and the quantity part of ITM-5.** A storeroom of individual rows does not fit the scene focus caps (`src/turn/context/scene-state-focus.ts:14,16`) or the 8-line goods cap, and name-string identity blocks a second identical item (`src/turn/authorization/command-authorizer.ts:50`). Quantity with split and merge rules has to exist before items move in and out of containers.
3. **ITM-1, canonical slot set and headwear/footwear categories.** The roadmap names equipment slots as a Property gate (`docs/MASTER_ROADMAP.md:131,140`), and Heartstone's authored rooms describe an equipment rack and a shoe rack (`data/locations/calderan/heartstone/heartstone_lr.yaml:66-70`) whose whole purpose is moving gear between body and storage.
4. **ITM-3, minimum part.** The possession invariant across containers and the decision on non-character owners (household or property storage). Today only characters can own items (`src/campaign/identity.ts:14-20`).

**Should be solved first (small, same code, strongly recommended):**

5. **ITM-6, equip and unequip action.** Without it the player cannot take a sword from the rack and wear it except through the `/equip` command that does not work for engine items.
6. **ITM-2.** Rides along with ITM-1 in `place()`; it also removes the second slot writer in SELL.
7. **SELL placement bypass (new, part of ITM-2 and ITM-3 work).** SELL rewrites `position` directly (`src/campaign/trade.ts:197-203`). With containers it must use the shared placement path, or selling a container would orphan its contents.
8. **DOC-12 and the stale comments in section 4.** Documentation only.

**Not required before Property/containers:** ECO-1, TRD-11, ECO-4, ECO-2, TRD-6, TRD-7, TRD-8, TRD-13, TRD-14. The exception: if the first Property slice includes buying, renting or selling property, or merchant stock held in containers, then D3 / ECO-1 and TRD-11 move in front of it, because a property price in the current whole-gold model cannot express rent anchors and would leave no ledger row.

**Non-item gates the roadmap also names (outside this review's scope, listed for completeness):** decision D5 (canonical NPC campaign records and NPC+), AUTH-5 (the implicit character record that `place()` creates through `characterForUpdate`, `src/campaign/items.ts:19,23`), and the A2 / A4 architecture items (`docs/MASTER_ROADMAP.md:131`).
