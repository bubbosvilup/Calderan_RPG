## DOMAIN 2. NarrativeContext and ControllerContext

### 2.1 Current behaviour

`buildTurnContext(world, snapshot, {input, recent_text})` (context-builder.ts:87-181) yields ONE `TurnContext` used as raw authority by three consumers:

- **Controller** (stages/controller.ts:37-48): `JSON.stringify({base_revision, context (minus npc_private_canon, npc_plus, player_profile.visible), explicit_intent, movable_characters, trade_offer?, referenced_known_characters?})` plus `final_narration` = the DRAFT. Internal IDs are intentional here. Not subject to the narrator token budget; only the 100k-char transport cap.
- **Narrator** (prompt-builder.ts:255-327): the same context re-rendered through `projectNarratorFocus` (foreground/background/compact), `buildSceneStateProjection` ("id-free account": location, time, weather, presence, items, resources, social, schedule), `[CURRENT AUTHORITATIVE CHARACTERS]` JSON per character, `[CHARACTER KNOWLEDGE ACCESS]` matrix (CAN USE / DO NOT USE per character), `[NPC-PRIVATE CANON]`, economic block, NPC+ flavour pack, dialogue-only recent history + bounded recent scene narration, retrieved canon (top-1 record + 3 awareness rows), controlled self-disclosure and interaction-partner blocks, then `mask()` over everything.
- **Audit** (stages/audit.ts): `projectKnowledgeAccess(context, retrieved,...)` and `JSON.stringify({context, retrieved})` as `authoritative_text` for price/procedure checks.

Contents (never-drop vs selected): location/ancestry/time/weather; every present person (+ items they carry, legal status, household membership, NPC+ packs); player profile (visible appearance narrator-only, households); Nicco-known facts (ranked, cap 32, with truth flag); knowledge edges for present people about shown facts; scheduled events (cap 16); social (relationships with Nicco unlimited, NPC-NPC cap 12, members cap 15, rules cap 12); price indices of present price-setters; `items_here`. Omissions are reported in `projection`. Objective identity vs player knowledge: `registerNarratorIdentities` (narrator-identity.ts:27-62) builds per-NPC `NPCn` refs, `player_known_name` (from Nicco's knowledge facts), `observable_label` ("the unfamiliar woman: ..."), and `mask()` substitutes unknown names/aliases/IDs in every INPUT string; output is never masked. Conversation partner objective identity is passed deliberately (`interactionPartnerBlock`) with a prompt-only non-disclosure rule. Retrieval is keyed on the player's input only, narrator+player visible canon only (secret candidates dropped), NPC use governed by `known_by`/`awareness`, not by retrieval.

Scaling shape: the context grows with PRESENCE, not with campaign age (good): fixed caps on facts/events, relationships bounded to people in scene. Unbounded dimensions: crowd size (characters, items they carry, CAN/DO NOT USE matrix is O(characters x facts), compacted losslessly else `context_too_large`), `snapshot.*` linear scans per build, and the Controller envelope (no token budget).

### 2.3 Recommended context-budget strategy
1. Make the budget two-sided and explicit: separate allowances (tokens) for FIXED (system ~3.3k), AUTHORITY (never-drop: location, present people, items, access matrix), FOCUS (ranked: facts, events, relationships, NPC+ flavour), RETRIEVAL (reserved 2.5-3k), HISTORY (dialogue + scene narration), OUTPUT. Today only the sum is checked, after the fact, and a breach is a hard `context_too_large`.
2. Degrade by tier, not fail: order of shedding = NPC+ flavour -> background actors to compact lines -> low-ranked facts/events -> NPC-NPC relationships -> older dialogue -> recent scene narration; AUTHORITY tier fails closed only if it alone exceeds the budget (already the access-matrix behaviour; extend to the rest).

## DOMAIN 4. Image generation

### 4.1 Current behaviour

- Flow: UI "Generate 3 avatars / 3 full body" -> POST `/api/portrait/generate` (server.ts:150-159) -> `GameSession.generateNpcPortraitBatch` (game-session.ts:480-593). Validate (idle, not busy, kind/pose from curated list, expected_revision, eligible target, adult gate, gallery room for 3) -> 3 parallel slots (`Promise.allSettled`) with distinct seeds -> stage bytes -> WAIT for session idle -> re-check eligibility and appearance fingerprint -> finalize files -> ONE `record_portrait_batch` commit (first avatar batch with no avatar: random pick among successes) -> expose. Failure after finalize deletes the files. Player (Nicco) and NPC+ share this exact path (`playerCapabilities`, same editor projection). Canonical NPCs without generated art show authored PNGs (`data/canonNPCAvatar`, 6 files, 2.1-2.5 MB each, 14 MB total) served by opaque token (canon-avatars.ts, server.ts:91-97).
- Prompt (campaign/portrait-prompt.ts): fixed line order: trigger + framing ("an adult fantasy RPG character...") -> details from the RESOLVED permanent appearance only (species/sex, apparent age, height/weight/build, skin/eyes, hair, scars, marks, traits, description capped 500) -> clothing (fixed modest) -> pose text from a curated id list -> background -> style -> constraints; separate negative prompt per kind. Free text is collapsed, de-quoted, capped (value 100, details 2000, total 3200). Sizes: avatar 992x992, full body 800x1200.
- Recovery (recoveryFor, image-generator.ts:58): `content_refusal` -> ONE retry with NEW seed + "modest" reinforcement; transient/429/5xx/timeout/network -> ONE retry SAME seed after 1-2 s; auth, credits, invalid, malformed -> none. - Storage: images as files under `saves/campaigns/<id>/portraits/...` (PortraitAssetStore stage -> finalize), metadata in snapshot (`record_portrait_batch`, prompt, seed, provider, style_id, billable_units, sizes). Gallery limit 64 versions per character; token per file = sha256 of (campaign, character, file) (portrait-assets.ts). Item sprites use the same generator (992x992) + a multimodal QA call on OpenRouter, up to 2 generations per item.
- Loading UI: client builds a "Generating 3 ... images" block, placeholders, elapsed seconds; stage text derived from elapsed time only ("Request sent" < 1 s, "Generating..." until 90 s, then "Taking longer than usual", client.js:258,289-302); client aborts its own fetch after 360 s (client.js:444).

### 4.3 The flaky test: `generation lifecycle (player|npc, fullbody): immediate progress block, placeholders, scoped disabling, completion refresh in the right bucket` (tests/ui-v1.test.ts:957-979)

Reading only (not run: no node_modules, and building would write `.build/` into the repo).

- The test is the only one in the lifecycle group that depends on wall-clock time: after releasing nothing yet it does `await wait(1150)` (a real `setTimeout`, line ~957 `wait = ms => new Promise(r => setTimeout(r, ms))`, defined at line 936) and then asserts `portrait-progress-stage` matches `/^Generating…$/` and `portrait-progress-elapsed` matches `/^[1-9] s$/` (line ~972).
- Those texts are written by `renderPortraitProgress()` (client.js:292-303), which is driven by a self-rescheduling `setTimeout(tick, 1000)` started in `startPortraitProgress()` (client.js:304-309), and computes `elapsed = Date.now() - startedAt`; `portraitStage` returns "Request sent" when `elapsed < 1000` (client.js:289-291).
- Cause (most likely): clock/timer skew plus tiny margin. The 1000 ms timer is scheduled on libuv's monotonic ms clock while the elapsed value uses `Date.now()` (wall clock). A timer can fire at 999 ms by `Date.now()` (known Node rounding: timers may run up to ~1 ms early relative to wall clock, more under NTP slew or when the process starts the timer mid-millisecond). Then `Math.floor(999/1000)` gives "0 s" and the stage stays "Request sent": both assertions fail. The test's own 1150 ms sleep leaves only ~150 ms of slack for the tick to have run and to have run late enough; under CPU contention (`node --test .build/tests/*.test.js` runs ~220 test files as parallel processes, package.json `test` script) the ordering/lag of the two timers is non-deterministic, and a loaded event loop can also let the component re-render with a stale `startedAt` if the `done`/hold sequence interleaves. It fails only for `fullbody` (and in both modes) presumably because those cases run when the machine is busiest after the heavier avatar cases; no code difference between avatar and fullbody explains it (same path, only the `kind` string differs).
- Secondary cause: `timer.unref?.()` on the tick means that if nothing else keeps the loop alive the timer may not fire; the test keeps the loop alive via its own `wait`, so this is not the primary issue.
- Not product-affecting (the real UI re-renders each second), but the test is nondeterministic. Suggested fix (not applied): inject a clock into `client.js` (or `mock.timers` in the test) and assert on the rendered value at 1000/1500 ms of FAKE time, or make `portraitStage` boundary-tolerant (`elapsed < 900`), and widen the wait. Classification: BUG (test), P3.
