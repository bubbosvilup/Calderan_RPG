## DOMAIN 1. CampaignState authority

### Current behaviour
- `CampaignState` holds one `#snapshot` (campaign-state.ts:85-88). The only writers of `#snapshot` are `constructor` (restore/new), and `commit()` (:129-138). `prepare()` (:106-109) is pure: it validates `expected_revision` against the snapshot (:56), clones the snapshot (:57), runs commands via one dispatcher (:60-63), then `invalidateStaleOffers` (:69) and `syncPremiumCharacters` (:71), then full `validateCampaignSnapshot` (:81). `commit` rejects forged/consumed receipts (:132) and receipts whose base is no longer current (:133). Commit is synchronous, so prepare->commit cannot interleave with anything in a single-threaded call chain.
- `expected_revision` is mandatory on every proposal (validation.ts:280, `integer(0)`), and the mannerism side-APIs carry their own (campaign-state.ts:113). So there is no "mutation without expected_revision" through the public API. The following callers pass `campaign.revision` read at call time (so the check is vacuous for them, by design): item sprite jobs (item-sprite-jobs.ts:39), portrait metadata commits (game-session.ts:574, 623, 689, 707), scenarios (scenarios.ts:35), opening state (opening-state.ts:27 uses literal 0 on a fresh campaign), structured-reflection maintenance (structured-reflection-maintenance.ts:155 uses `source` = revision it read).
- Mutation entry points into the campaign (all via `prepare`/`commit`): TurnCoordinator single commit (turn-coordinator.ts:225); `GameSession.acceptTradeOffer` (:380); `completeHeartstoneRite` (:353); `updateNpcAppearance` (:418); `updatePlayerProfile` (:445); `overridePlayerLocation` (:324-325); portrait batch/roles/reference (:574, :623, :689, :707); item sprite jobs; post-turn mannerism + reflection maintenance; load-time canon reconciliation (canon-compatibility.ts:97-99, bumps `revision` on a draft snapshot before `CampaignState.restore`).
- Who may mutate what from prose: the State Controller can only propose kinds that `authorizeCommands` explicitly handles; `default:` rejects (command-authorizer.ts:132). `set_funds`, `transfer_person`, `set_legal_status`, `accept_trade_offer`, `invalidate_trade_offer`, `register_character`, `set_profile` are not in the controller schema (controller-schema.ts only exposes propose/withdraw trade, see :40-44). Engine-derived (deterministic, from player input or delivered narration) commands bypass the controller: `manumit` (person-transactions.ts), `register_character` + `set_profile` (name-establishment.ts:61,76), person `propose_trade_offer` (person-offers.ts), canonical-name `set_knowledge` (commit-preparation.ts:47), contract commands.

## DOMAIN 3. Actual Offer

### Current behaviour
- Data: `TradeOfferRecord` (types.ts:139-147), ledger `snapshot.trade_offers` (optional additive, types.ts:297). One active offer max (snapshot-validation.ts:144). Statuses: active/accepted/superseded/withdrawn/invalidated.
- Creation: goods (BUY lines / SELL existing item ids) from the Controller via `authorizeTradeProposals` (evidence = verbatim quote in the **draft**), person (BUY only) from `resolvePersonOffers` on **delivered** narration (commit-preparation.ts:59-70). A turn that already carries a goods offer skips the person reader (:59).
- Lifecycle: `propose` supersedes the standing offer unless `sameOffer` (trade.ts:133-135); `withdraw` (Controller + regex `WITHDRAWAL`, trade-authorization.ts:55-63); `invalidate` automatic after every prepare (`invalidateStaleOffers`, campaign-state.ts:69) for scene change, absent counterparty, item gone/not held/referenced, person unavailable (trade.ts:62-88). Insufficient funds deliberately does not invalidate (:60).
- Settlement: only `accept_trade_offer` (trade.ts:153-207), only from `GameSession.acceptTradeOffer`. BUY goods: debit `price`, create one item per line via `create_item` (carried, owner=player, never equipped, purchase acquisition) (:161-177). SELL: delete items (:178-193), credit player. PERSON: replays stored plan, ledger transaction by `transfer_person` (:194-204). Offer becomes `accepted` with `settlement` (:205).
- Masking: player card derives from the closed lexicon `ADJECTIVES/NOUNS` and the "Slave" provisional label (trade-offer-view.ts:40-50, 58-66); `session-view.ts:69-70` and `player-character-view.ts:151-153` apply "Slave" for unnamed enslaved created characters; rename is a `set_profile` on the same id (name-establishment.ts:61), the offer `ref` is `sha256(campaign:offer_id)` and never changes.
- Save/load: offers persist (validation.ts:226-228, snapshot-validation.ts:142-155). A pending person offer holds `ephemeral_ref` (`scene_npc_...`) from a session-local registry that is NOT saved; acceptance still works because the plan is self-contained, and `retireParticipants` is a no-op after load.
- Vendor/Auction: no vendor model. Auction exclusion = `auctionPlace` regex on location name (trade-authorization.ts:49) + `AUCTION` word regex on the sentence/quote (:23,74); person offers have a weaker version (person-offers.ts:59).
